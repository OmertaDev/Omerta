# Bounded high-player-churn component

This is a roster/enrollment component, not a complete RC1 workload or qualifying matrix cell. `tools/rc1-churn-policy.js` does not read the database or make network calls. Only the native exercise's observer reads canonical database state; those observations never inform retirement selection or enrollment identity.

For each completed week the runner supplies the recorded **actual active** current account IDs. At a quiescent boundary, `floor((3 * activeCount + remainderTenths) / 10)` actors retire and the remainder is carried modulo ten. Thus 25 active actors produce 7, then 8 replacements; 28% and 32% are the honest individual-week fractions. Cumulative replacements equal `floor(0.30 * cumulative weekly active counts)`. Zero activity produces zero replacements. Selection sorts seeded hashes of week and current account ID; input ordering does not affect selection. Random native account IDs must be retained for repeatability; no fresh-world equivalence is claimed.

## Runner contract

Create with `{seed, epochAt, initialRoster:[{accountId, characterId, sessionRef}]}`. `previewWeek({week,logicalAt,activeAccountIds})` is read-only. `beginWeek` checks consecutive due weeks, rejects foreign/retired/duplicate active identities and unresolved enrollment, then removes the selected accounts from the current cohort. Stop their sessions immediately, retaining every canonical account and commitment in lifetime observer/resource coverage. Do not ban, kill, delete, cancel, transfer, revoke credentials or change deadlines to simulate departure.

`nextEnrollment()` returns a durable request identity and phase. For the guest phase the caller creates a cryptographically random 32-byte base64url bootstrap secret, privately persists it under `credentialRef` **before dispatch**, and calls ordinary `POST /v1/auth/guest`. Recover a lost guest response with the same secret. Verify the returned bearer identity, persist the bearer under a new `sessionRef`, then call `settleEnrollment({requestId,phase:'guest',status:'COMPLETED',accountId,sessionRef})`. This registers a lifetime account, but does not yet make it current.

The character phase returns the exact authenticated path/body/idempotency key. Persist pending state before calling it. Bootstrap recovery retires at character creation, so subsequent recovery uses the persisted bearer and the same character key. Settle only the canonical result using `{requestId,phase:'character',status:'COMPLETED',accountId,characterId,idempotencyKey}`. Exact repeated receipt settlement is a no-op; conflicting receipts and old account/character identities fail. Lost responses and denials retain pending work, and do not create a second enrollment key. The caller records attempts/denials/replays separately. Canonical HTTP identity verification belongs to the runner; passing arbitrary synthetic receipts proves only the component's unit behavior.

`roster()` separates current IDs, retired IDs and lifetime registered account/character identities. During partial entry the current cohort is smaller and lifetime includes accounts without characters. `summary()` reports all three counts and incomplete enrollments. `checkpoint()` contains opaque credential/session references, request identities, receipts and the roster, never raw secrets. `restore()` reconstructs and validates every transition. Actual secrets/bearers require a separate restricted durable store; losing that store is not repaired by inventing credentials.
