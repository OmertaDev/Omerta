## Architecture and public interfaces

- `worldgraph.js` owns immutable authored definitions. `world-kernel-query.js` resolves a bounded player-specific graph from existing domain tables, using stable encoded references. It stores no copies of accounts, characters, Crew/Family membership, inventory, knowledge, mystery or operation state.
- `createWorldKernelQuery({pool, knowledge?, registry?}).snapshot(accountId, {limit?})` returns version 1 nodes, typed relationships and explicit truncation flags. Authentication supplies `accountId`; the client cannot nominate another inventory owner. Snapshot consistency uses one PostgreSQL repeatable-read transaction.
- Current Crew affiliation to a Family is derived only when every living member belongs to that Family. It is a query fact, not permanent affiliation or delegated mutation authority. Mutations lock and recheck current memberships.
- Existing accepted, unexpired Family pacts appear as `alliance` relationships with `kind: pact`; active wars appear as rivalries. Public coalition summaries retain their existing target/count visibility and disclose only the requesting Family's membership edge. Current-Crew weekly objectives use the original `(crew_id, week)` identity, deterministic unmaterialized fallback and own contribution fields. A single server timestamp governs expiry and week selection. These views grant no diplomatic or objective mutation authority.
- `createWorldKernel({pool, registry, objects, enabled, knowledgeEnabled, sharingEnabled, accountIds})` provides `list(accountId)`, `get(accountId, objectId)` and `execute(accountId, {objectId,actionId,itemId,expectedRevision}, key)`. Only compiled state transitions can change physical objects; a current boss/underboss, a uniform living Crew, location, authentic knowledge, own item and required materials are checked server-side.
- `compileWorldObjects` defines facility/workshop/object identity, location, states, visibility and transitions. Existing territory/economy tables remain authoritative for their domains. New physical objects live in `world_kernel_objects`; immutable transitions live in `world_kernel_events`.
- `withItemTransaction` remains the sole transaction owner for world actions, item consumption, provenance and retry receipts. Item guards namespace logical world keys by authenticated account. Events commit with state; process-local `world:changed` notifications are invalidation hints only.
- `normalizeKnowledgeRequirement` pins a discovery content hash, domain, proposition, source root and typed value. `createCoordinationKnowledge().matchesRequirements` checks original authenticated claims under current ACL/membership locks. It locks the complete candidate union in global ID order. No knowledge is copied or minted by crafting.
- Crafting adds the `knowledge` condition adapter and server-configured knowledge/sharing/cohort switches to `createCraftingContext`. `recipeCatalogForPlayer` supplies a truthful, redacted board. `craftWorldGraphRecipe` and `salvageCar` retain their existing mutation contracts and re-evaluate knowledge inside the transaction.
- `worldKernelInvariants` reconciles current object state, contiguous revisions, immutable events, consumed items and durable receipts in a consistent snapshot. The existing invariant sweep includes it.

Domain equivalents are intentional: players retain their account/current-character split; districts represent territory and location; physical objects use facility/workshop/object kinds; item instances and resource balances remain in the existing item ledger; knowledge claims carry discovered information and authenticated source evidence; mysteries and operations remain references to their existing engines. No duplicate alliance, clue, inventory, objective or location store was introduced.

## Coordination Engine Core

`createFamilyOperations({pool,registry,kernel,definitions,enabled,knowledgeEnabled,sharingEnabled,accountIds})` exposes `catalog(accountId)`, `get(accountId,operationId)`, `create(accountId,{definitionId},key)` and `command(accountId,operationId,action,input,key)`. Catalogs include at most 50 current-Family instances; history exposes the latest 100 entries with explicit truncation. Definitions accept 2–8 distinct account seats and at most 32 requirements. Fixed participation, item, resource, gameplay cash, information and character capability requirements separate promises from fulfilled contributions. One primary item and the exact World Graph action materials prevent unaccounted extra consumption. Pinned hashes include the world definition.

Family mode uses `world_operations`, `world_operation_roles` and `world_operation_contributions`. New commitments, capital escrow and immutable event tables add missing facts rather than duplicate inventory or world state. Legacy Crew mode retains its unique identity and guarded lifecycle; Family runs use an independent server-generated run key. Legacy reads, writes and replay entry points reject Family rows.

The lifecycle is draft → recruiting → committed → ready → executing → resolving → completed, with failed/canceled/expired terminal alternatives. `publish`, `join`, `assign`, `leave`, `commit`, `contribute`, `withdraw`, `approve`, `execute`, `cancel` and `expire` enforce current authority. Officer assignment reserves a seat without spending the assignee's assets; contributions require that player to act. Changes to seats or commitments clear approval. Readiness is derived from locked current characters, membership, authenticated evidence, physical state and actual custody; persisted READY is never sufficient authority. Explicit expiry performs refunds; reads never expire or resolve operations.

Every command owns one item transaction and one account-scoped replay receipt. The coordinator locks the caller's Crew, the complete sorted current/historical character union using native NOWAIT, accounts, Family/memberships and operation. It revalidates the union before fresh mutation. Completed exact-key replay bypasses fresh-work union/definition checks after current account/read admission. A new command whose union changed receives contention. Grouped knowledge proof preparation locks the complete candidate union once; `kernel.executeInTransaction` verifies the branded proof and consumes operation escrow under the same root. Executing/resolving transitions, the world event, contribution history, item/resource/cash changes and final receipt commit atomically. Notifications are best-effort postcommit invalidation hints.

Cash is existing gameplay `characters.cash`, capped at 1,000,000 per authored requirement, never $OMR. Deposit debits the authenticated living character. Withdrawal returns exactly the held amount to the original living character; a dead/missing original forfeits it and an heir receives nothing. Resolution spends held capital. The four exact `coordination:capital:*` ledger reasons reconcile held cash independently. Materials move by consumed-input credits within one mutation; no cross-owner grant can reuse an input. Unique-item refunds use the recorded depositor. Cancellation remains available to the opener or current officer after affiliation changes; recovery uses persisted escrow even if the current definition changed.

`GET/POST /v1/coordination/operations`, `GET /v1/coordination/operations/:operationId` and `POST /v1/coordination/operations/:operationId/actions/:action` are authenticated, strict-input routes. `COORDINATION_OPERATIONS=on` additionally requires `COORDINATION_ENGINE=on` and `WORLD_GRAPH_KERNEL=on`; knowledge/sharing/cohort policy is reused. All switches default off. Boards hide raw knowledge predicates, sources, discovery identities, resolution seeds and other players' account/character IDs. A private Family operation and a nonexistent operation share the same unavailable response.

The four-player Foundry pilot demonstrates real Crew/Family membership, discovery and sharing, salvage, knowledge-gated crafting, promises, item/material/cash escrow, approval, atomic world resolution and newly public archive visibility. General resolution supports a persisted seed, bounded chance and verified character stat/level modifiers; retries cannot reroll. The shipped pilot is deterministic and produces no reward faucet.

## Player-specific World Projections

`GET /v1/projections/player` versions the existing player read/accrual result as `{schemaVersion:1,asOf,player}`. Character, Crew, Family, location and the major existing game boards continue to use that established player authority. `GET /v1/projections/world?operationId=...` composes Player, Crew, Family, Territory, Inventory, Knowledge, Operation and Activity cards, visible world objects, recipes and authorized mystery/operation references. It reuses `WORLD_GRAPH_KERNEL` and the existing account cohort; operation cards also honor `COORDINATION_OPERATIONS` and knowledge/sharing switches. Both routes require authentication, reject extra query fields and set `no-store`.

`createWorldProjection(...).snapshot(accountId,{operationId?})` owns one `withItemRead(pool)` boundary: PostgreSQL REPEATABLE READ READ ONLY, with the existing pg-mem read/write barrier in memory tests. It plans all recipe, world and selected-operation predicates first. `knowledge.readSnapshot` authenticates a complete union of at most 256 claims for at most nine actors and 64 predicates once, under that same snapshot. Private brands bind the result to the exact active read scope, database client and viewer; it cannot be used as an executable knowledge proof. Overflow fails closed. One server-owned timestamp governs time-sensitive facts. The established player accrual endpoint is a separate snapshot and is not falsely presented as atomic with the world read.

The internal graph facade becomes explicit DTO fields before serialization. Raw graph relationships, hidden predicates, source roots, proof tokens, resolution seeds and other participants' knowledge are absent. Owner-only knowledge grants remain available; other participants expose aggregate readiness. Recipe and world action eligibility uses complete authoritative inventory counts, independent of the 50-card display limit. Selected operations expose explicit server-calculated actions and safe missing-requirement codes. Reads never approve, expire, resolve, spend or mutate state. Commands revalidate current locked authority; projection eligibility is advisory.

The World board displays knowledge differences, item/resource custody and safe provenance, recipe requirements, visible objects, Family role requirements, readiness and history. It invokes the existing guarded commands and retains an uncertain command's original idempotency key for reconciliation. Player and world refreshes use session/character epochs and coalesced requests; invalidation during an in-flight read queues a replacement and removes stale controls. Logout and character replacement discard stale results.

`projection-events.js` translates postcommit world/operation events and successful HTTP mutations into identifier-free `{channel:'projection',changed:true}` hints. Claim sharing/revocation targets actual grant audiences; Family operation notifications use Family/opener/participant/history visibility, not shared Crew membership. Private discovery and generic private actions refresh only their actor. World transitions fan out publicly only when a durable event names a public state. Membership changes invalidate old audiences and reconnect affected sockets. Private Crew/Family feeds revalidate account, token, current character and membership before forwarding. Hints are best-effort within the existing process-local bus; there is no durable cross-process notification queue. Reconnect/manual refresh recovers durable state.
