# Funded transit protection

This bounded N28 component starts from the N20 documentation successor `ba64a1d925ab0fb224adf046fe36a125d5f8e184`. Its dependency is the actual N20 native component and its seven explicit shared proposals. This is an implementation design, not a deployed service or native qualification.

The payer is the actual current carrier of a genuinely funded first or second N06 courier leg linked to an active N20 campaign. The payer protects its own original character. The guard is the actual original N20 guard, at that guard's current canonical price. No player can fund coverage for another account, invent a cargo title or substitute another provider.

Funding reserves only the original payer's game cash. It uses a solo root and creates no guard membership or known-player relationship. The original guard separately accepts the exact terms through its own solo root. Only accepted, request-ACK-bound terms can derive the guard for actual activation. Activation is initiated by the original payer, uses the existing Game payer/guard pair and canonical courier-aware prelocks, releases only that payer's reserved cash, then immediately buys the actual bodyguard service at its unchanged fee and tax. The guard receives no authority to spend any other payer balance.

The purchase window is bounded by the actual original courier leg and expiry. The delivered coverage has the canonical service's actual expiry and conditions. `meet:true` does not enforce co-location; actual activation still independently passes the existing known-player gate. Solo funding and acceptance do not manufacture a meeting. The guard may cover other principals; a successful save consumes an assignment and the atomic guard-availability claim can serve only one concurrent save. Jailhouse shanking bypasses street bodyguards. This provides no prison shield, building armor, cargo reimbursement, exclusive guard promise or guarantee against every attack.

One payer can have one outstanding reservation. Only accepted pending contracts occupy the guard's single pending metadata slot. Unsigned foreign offers do not add a guard to any action or estate census. Guard withdrawal, actual guard death or bounded stale-slot retirement blocks only participation metadata. The original payer retains a direct claim to its own unused reserve. A payer estate resolves only that payer's bounded unused reserve before the existing estate disposition; no peer cash is written. Activated contracts hold zero reserve and retain actual paid source journals and historical coverage evidence.

Canonical source completion, leg changes, N20 retirement, guard price changes, original replacement and actual expiry must refuse activation without consuming the reservation. Original refunds stay available without depending on a surviving guard or live source leg. Real source ACKs, original actor/account ACKs, fresh source-owned proof and clocks must all validate in the actual transaction. No N20 receipt or proof constructor grants protection authority.

Live financial activation, external payments and paid compute remain disabled. This service uses existing game cash and the genuine canonical guard effect; it makes no onchain burn or real-income activation claim.

The closed actions are `fund`, `accept`, `activate`, `refund`, `expire` and `withdraw`, served through the same authenticated routes for human and agent credentials. Fund bodies name only an actual campaign reference, exact quoted game-cash price and bounded lifetime. Later bodies name only the contract/hash and explicit consent. No body accepts a guard override, another protected player, actor list, source receipt, callback or spending envelope.

The source-owned N20 view checks the existing immutable campaign, six original consents, completed manufacture and guard prerequisites and typed N06 link. The independent N06 view checks its actual original owner reserve, actual earned-fee journals, two canonical carrier consents and current same-UID operation custody. These views are read-only evidence. They create no canonical ACK or freshness witness. N28 activation uses only the actual payer/current carrier and guard as mutable Game cash snapshots. The existing N06 owner and two carriers are already derived lock/read roots, overlapping the current carrier; checking their presence in the genuine private rental scope grants no third-party cash write. Game's pair arity and canonical actor caps stay unchanged.

The finite estate census is derived directly from two partial unique indexes: at most one outstanding reservation as payer and one accepted pending membership as guard, hence at most two N28 rows for an original character. Unsigned funded offers and zero-reserve historical purchases do not enter a guard census. The bridge needs no peer character, additional death counterpart or new root hook. Payer recovery credits only the actual original victim's own reserve before the ordinary estate disposition. Guard recovery changes only accepted metadata. A subsequent payer refund needs no surviving guard or campaign. Stale accepted-slot retirement observes one indexed prior membership and changes only metadata; historical canonical sources and obligations remain intact.

Actual activation still uses the canonical known-player rule: with the ordinary meeting option, a remote guard requires existing genuine knowledge; co-located canonical dealings may create the normal completed meeting. Funding and guard acceptance create neither contacts nor a location sighting. The staged eligibility rechecks do not promise an atomic six-character liveness transaction. Actual source and final ACK checks refuse a dead, replaced, expired or changed original before paying; independent legitimate source actions remain valid if campaign metadata retires.

This component's declarations and owned source are separate from coordinator-owned shared proposals for Game's two fixed finalizers, Social's independent private one-use witness, N20/N06 read-only qualification, estate recovery, schema and route registration. Their literal N20 dependency hashes are retained separately from Git base blobs. Source-pinned native evidence, required integrated security/release checks and verified production deployment are distinct phases.
