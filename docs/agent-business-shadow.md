# Agent business management in shadow mode

The business layer observes funded work and records proposals. It cannot bid, change a service price, send a customer message, buy compute, approve work or change an owner spending policy. Existing financial rails remain separately gated.

## Company registration and premises

An owner session can register or update one company profile per account with `POST /v1/resources/company`. Supply exactly `expectedRevision` (0 for registration), `name` (2–64 plain characters), `published` (boolean), and `premises` (null, `estate` or `street`). For example:

```json
{"expectedRevision":0,"name":"Docks Company","published":true,"premises":"street"}
```

The authenticated account determines ownership; callers cannot supply another account or add authority fields. Delegated agents can read their account's profile with `GET /v1/resources/company` but cannot publish or change it. This metadata operation works while external resource intake is disabled and creates no treasury, ledger entries, asset rights or spending permissions. Revision checks reject stale concurrent changes. Names are display labels, not globally unique identities; the account ID identifies the company profile.

`GET /v1/resources/companies/:id` exposes only published profiles. Existing enabled storefronts include their published company profile and mark an operational association only while its selected premises verify. Estates require an acquired tier; streets require current account ownership of the same internal deed identity and district, with no pending/extracted on-chain token. Temporary corner control is insufficient. Transfers, renames, extraction and same-district replacement deeds invalidate the old binding; reads return `verified: false` without stale location fields. Rebind by updating the profile with the current revision and selecting owned premises again. Set `published: false` and `premises: null` to withdraw a profile after ownership loss. Reads describe current game records, not an atomic guarantee against a later transfer or independently verified chain ownership.

Company profiles do not create separate balances, employees, banking rights or a new legal entity. [The next ten recommendations](agent-company-roadmap.md) propose those later operating layers as separately reviewed work.

Autonomous gameplay is separate from this read-only business observer. `tools/agent-alpha.js --role business` executes issued front purchases, upgrades, upkeep and collection alongside existing depot duties, using server-revalidated action IDs, transaction locks and replay recovery. Its conservative strategy is optional; ordinary authenticated gameplay APIs already allow custom agents to play the same business, borrowing and combat systems as humans. Game cash is not withdrawable USD. The paid-work modules currently lack seller bank/wallet payouts and human-authored deliverable submission, so neither internal USD credits nor test receipts establish withdrawable real-world earnings. Those funded earning and settlement capabilities require a separate reviewed release; payment and real compute activation remain disabled.

`GET /v1/resources/business` requires the account's bearer token. It returns actual settled ledger revenue, paid-work compute expenses and unresolved reservations, bounded job/call details, active capacity, repeat-customer counts, configured compute quotes and descriptive provider outcomes. It omits questions, reports, prompts and provider outputs. Global totals retain receipts outside the 100-job/100-call detail window; coverage flags disclose truncated details. Snapshot time is captured after acquiring the existing treasury lock. The observer creates no treasury and runs no mutation SQL.

Run `npm run --silent agent:business -- --samples 5 --provider <capability-id> --max-output-tokens 256 --target-margin-bps 2500 --minimum-margin-usd-micros 10000` with `OMERTA_BUSINESS_TOKEN` supplied securely in the process environment. Tokens are never accepted as command-line arguments or included in records. The command prints a bounded JSON record to stdout; save it in an owner-private location if retaining financial observations. `--previous <previous-record.json>` compares the first observation with the last evaluation in an earlier saved record. Prior files are operator-owned observations, not independently verified evidence. No file is transmitted to the API.

The default policy targets a 25% gross margin on known compute costs plus a one-cent minimum margin, at most three active jobs and five proposals. Target margin basis points are bounded at 0–9000; proposal count at 1–10. The selected provider's full configured input limit plus requested output limit supplies a conservative quote. Prices round up to exact cents and must fit existing market bounds. Each proposed job reserves compute funds and daily authority in the simulation so multiple proposals cannot reuse the same budget. A frozen treasury, expired/disabled owner policy, denied provider/retention authority, unresolved calls or incomplete detail coverage blocks bid proposals.

Use `--duty sales` to focus on bids, service pricing and repeat-customer review, or `--duty fulfillment` to focus on awarded delivery. The default `--duty general` retains both. Filtering happens before the proposal limit, so urgent delivery does not crowd out sales recommendations in a sales observation. All duties still calculate the same awarded-job and pending-bid protection, capacity and risk flags. A fulfillment observation with no applicable delivery returns a hold. Duties are local shadow-planning preferences, not employee identities, owner-approved assignments or access-control permissions; current account-wide agent keys cannot distinguish individual workers. No procurement duty is available until the planner has concrete procurement recommendations. Previous observations continue to measure outcomes of their original proposals, even when the next observation uses another duty.

Awarded jobs due within an hour receive delivery priority. Expired jobs are flagged for recovery and never recommended for execution. Suggested service prices and repeat-customer follow-ups require owner approval. No automatic messages, subscriptions or renewal purchases occur. Provider availability is not guaranteed by a price quote; existing broker constraints still apply before any future execution.

Before proposing new bids, the planner protects one full configured compute quote for each open or claimed job against available cash after the minimum reserve and the remaining daily allowance. Earlier recorded compute costs do not prove an unfinished job can be delivered without further compute, so this allowance is deliberately conservative. Submitted, accepted, disputed and refunded jobs receive no new delivery allowance. `deliveryBudget` reports the visible pending-job count, `protectedComputeUsdMicros`, `cashCovered` and `dailyBudgetCovered`; these are planning observations, not reservations or approval. Missing quotes, incomplete details, mismatched active-job counts, and invalid or expired pending deadlines make protection unknown (null) and hold new bids. Duplicate job IDs are rejected. Existing owner authority and per-call constraints still apply independently.

The authenticated snapshot also reports `commitments.pendingAwardBids`: a complete aggregate of this account's bids on open, unexpired bounties from other buyers whose service revision still matches its enabled offering. This count is not limited by the 100-record detail window. Expired, cancelled, awarded and stale-revision bids are excluded. Buyer funding/authority and future awards are not guaranteed by this count.

After protecting awarded delivery, `bidCommitmentBudget` protects another full configured quote per pending bid against cash and daily allowance, and `capacity.pendingAwardSlots` reduces planning slots before proposing new bids. `capacity.reservedSlots` keeps its existing active-job meaning. These are deliberately conservative potential commitments: multiple buyers might choose an agent, while actual award still enforces the current capacity and authority checks. Missing counts in older saved snapshots, unknown costs/quotes and unsafe combined arithmetic remain null and hold new bids. Cash/daily coverage fields describe amounts only, not authorization. No actual reservations or owner policy changes occur.

Each record includes proposals, job economics, capacity and risk flags. Subsequent observations match suggested bids to awarded job IDs and report observed acceptance, receipts and expenses. They compare service-price changes and repeat accepted work without attributing those changes to the observer. `causalEffect` remains null, outside costs remain incomplete and net profitability remains unknown. Model outcomes are descriptive; deciding whether stronger models improve quality needs a controlled comparison.

The observer supports 1–20 samples, a minimum 3100ms request cadence, a 30-second request deadline and bounded response/record sizes. It uses GET only, pins credentials to the selected HTTPS origin (loopback HTTP is allowed for tests) and refuses redirects. There is no live-execution mode. The isolated resource pilot records shadow proposals alongside six simulated bounty-to-acceptance cycles; synthetic demand and test funding do not prove organic revenue or causal improvement.

## Estimated operating costs and payment fees

Use `--operating-cost-per-job-usd-micros` for estimated fixed per-job costs (including any allocated flat processor/hosting/labor expense), and `--payment-fee-bps` for an estimated percentage fee. Both default to zero. One USD is 1,000,000 micros; 290 basis points is 2.9%. Operating estimates are bounded at 1,000,000,000 micros and percentage fees at 0–3000 basis points. Target margin plus percentage fee must remain below 100%.

Suggested prices cover the larger of configured compute quotes and measured job compute costs, then fixed estimates, estimated percentage fees and the target margin. Percentage fees round upward to exact cents; pricing includes a conservative one-cent rounding reserve when a percentage fee is configured. If the resulting price exceeds market bounds, the planner holds rather than proposing an invalid price. `estimatedContributionUsdMicros` includes these estimates; existing known compute-only contribution stays separate.

Estimates never become ledger expenses, treasury reservations or owner spending authority. Compute reservations still use the configured compute quote only. Records flag operator assumptions as unreconciled; `outsideCostsComplete` and `profitabilityKnown` remain false. Actual billing reconciliation is still required to establish net profit.
