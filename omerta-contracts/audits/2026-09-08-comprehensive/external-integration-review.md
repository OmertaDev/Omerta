## CCA: entry, custody, settlement, and recovery

The OMERTA builder uses native ETH as currency, zero validation hook, 4,410,000 OMR for auction supply and 1,653,750 OMR reserved for LP. It places the known LBPStrategy in `fundsRecipient`, the configured treasury in `tokensRecipient`, the proceeds splitter in migration `recipient`, and the separately configured LP NFT recipient in `positionRecipient`. Those recipients serve different custody functions and must be reviewed independently before signing.

The CCA factory decodes the same `AuctionParameters` tuple encoded by `src/genesiscca.js`. It namespaces CREATE2 salt by caller, and substitutes the special address(1) recipient only when explicitly configured. OMERTA supplies concrete recipients. `onTokensReceived` checks the full sale balance before setting the auction-active latch; it is permissionless but does not transfer tokens, rewrite allocations, or set recipients.

`submitBid` requires the auction to be started and funded, refuses bids at/after END_BLOCK, refuses zero amount/owner, and requires exact `msg.value == amount` for the selected native-ETH path. It checkpoints before adding a new bid, so the new bid cannot earn the prior period's issuance. The supplied owner receives both the eventual refund and tokens; callers cannot redirect another bid's stored recipient at exit or claim. The validation hook callback is disabled by OMERTA's zero address. General ERC-20 currency and custom validation-hook semantics are consequently outside this integration conclusion.

The issuance schedule is stored via SSTORE2 and constructor-validated: each duration is positive, packed lengths are eight bytes (`uint24 mps | uint40 blockDelta`), cumulative `mps * blockDelta` equals 10,000,000, and total duration lands exactly on END_BLOCK. OMERTA uses the matching packed format and validates the same totals, including a meaningful final-block tranche. Claims require CLAIM_BLOCK >= END_BLOCK; the builder additionally requires claim time at or after migration time, with migration at END_BLOCK + 1.

Accounting stores aggregate currency/supply in Q96 times 1e7 and records each bid's cumulative schedule point. Clearing prices never decrease, demand is normalized by the remaining schedule, and tick traversal subtracts outbid demand before raising price. Token fills round down for individual bidders; the global cleared amount rounds up and is capped at total supply. Currency spending rounds up, refunds round down, and the refund calculation saturates at zero for a possible one-wei spending-rounding excess. Aggregate dust can remain unsweepable; exact exhaustion of all wei is not a supported property. These rounding directions favor retained solvency, although this manual trace is not a formal proof of every arbitrary parameter combination.

`exitBid` finalizes fully filled bids after auction end. `exitPartiallyFilledBid` validates linked checkpoint hints, the transition from fully filled to partial/outbid, and graduation before an early exit. If the auction ends without graduation, either exit route refunds the entire bid and records zero tokens. `_processExit` sets `exitedBlock` and `tokensFilled` before refunding ETH. A reentrant refund recipient cannot exit the same bid twice; other exited bids still follow their own stored accounting. A recipient that refuses ETH can block its own refund; it cannot redirect or force the treasury to consume refund liabilities.

`claimTokens` and `claimTokensBatch` require the claim block and graduation. They require the bid to have exited and zero the stored `tokensFilled` before token transfer. Batch claims check each stored owner against the requested batch owner; a duplicate ID contributes zero after its first inclusion. Permissionless execution of another person's claim sends to that person, not the caller. ERC-20 OMR is the selected output; no arbitrary-token callback compatibility is claimed.

`sweepCurrency` is callable only by the stored LBP strategy, after auction end/finalization and once. It transfers only recorded currency raised (less protocol fee), leaving bidder refunds in the auction. A failed auction marks a zero sweep and retains all ETH for full refunds. `sweepUnsoldTokens` is callable only by the configured treasury and once; graduation returns the computed remainder, while failure returns all auction supply. Sweep markers are written before external transfers and reverted with the transaction if transfer fails. The LP reserve belongs to the LBP migration/recovery path and is not held in the CCA; it must not be confused with CCA's unsold-supply recovery.

Tick-spam can increase checkpoint gas. The explicit `forceIterateOverTicks` path advances the sorted active tick list in bounded caller-chosen portions, checking that a supplied endpoint is initialized and ahead of the current pointer. This is an available progress mechanism, not proof that every stressed auction will finalize within any chosen operational time limit. A keeper must know how to drive it if ordinary finalization exceeds a block's gas budget.

## CCA fee and clock trust boundaries

The factory's fee controller address is immutable; the controller's fee policy may remain mutable. `lbpInitializationParams` queries it at read time and subtracts the quoted fee; `sweepCurrency` queries it again and clamps fees greater than raised currency. The imported fee helper treats a reverting amount query as zero, but fee transfer separately calls `protocolFeeRecipient`. A nonzero, mutable, or malicious controller can therefore affect the net migration amount or liveness. Preflight checks all six configured runtime hashes and immutable links and reports the current fee/controller information, but one representative raise is not a guarantee for every eventual raise, nor is an off-chain read an immutable fee commitment. The root's retained runtime verification determines whether the actual factory has a zero controller. Re-evaluate if that pin changes.

The pinned BlockNumberish dependency chooses ArbSys `arbBlockNumber()` when the 0x64 precompile exists and returns a valid word; otherwise it uses `block.number`. OMERTA's readiness comparison uses RPC latest block number, while cadence evidence explicitly records BlockNumberish. A read-only same-block check during this review returned chain 4663, RPC block 57,414,349, one-byte ArbSys code, and ArbSys block 57,414,349. This invalidates a clock-mismatch hypothesis for that observation, but remains a point-in-time live-chain check; the fork's local clock shim is a separate test assumption. Retained JSON: `external-clock-observation.json`.

`GENESIS_LAUNCH_PHASE` closes Desk and bond surfaces through preparation/auction/migration/oracle warm-up, with existing Desk fills permitted in prepare. Its default `legacy` deliberately leaves those gates unarmed. The environment setting is an operator interlock; it is not an on-chain CCA state oracle and cannot accelerate CLAIM_BLOCK. Production activation must set the correct phase and only advance to live after the canonical pool/oracle checks in the release process.

## Safe: concrete deployment and governance boundary

The checked-in example addresses are singleton `0x29fcB43b46531BcA003ddC8FCB67FFE91900C762`, factory `0x4e1DCf7AD4e460CfD30791CCC4F9c8a4f820ec67`, and compatibility fallback handler `0xfd0732Dc9E303f09fCEf3a7388Ad10A83459Ec99`. This review did not certify those addresses' production runtime bytes.

`DeploySafe.s.sol` uses `createProxyWithNonce` with the complete `setup` payload in the same factory transaction. Setup's delegatecall target is zero, data empty, initialization payment zero, and the fallback handler explicit. With authentic source/runtime, no uninitialized proxy interval is exposed and no module is installed during this ceremony. Factory CREATE2 incorporates the initializer hash, so changing owners, threshold, or handler changes the predicted address. This method is not chain-specific CREATE2; transaction signatures still use a chain-ID and Safe-address EIP-712 domain.

Safe setup validates nonzero threshold, no duplicate/sentinel/self owners, and one-time initialization. Deployment verifies exact owner order/count, threshold, nonce zero, and reported version; the mainnet wrapper additionally requires exactly three unique owners and threshold two. Governance execution binds target, value, data hash, call/delegatecall operation, gas/refund fields, and nonce. Signers must be increasing unique members, preventing duplicate-signature threshold inflation. Nonce consumption occurs before external execution. Signature-related helper methods that allow an explicit number of signatures do not themselves execute transactions; the actual execution path supplies the stored threshold.

Owner, threshold, handler, module, and guard changes require a Safe self-call. Enabled modules have a separate arbitrary-execution path without owner confirmations. Guards can block execution and do not constrain module transactions in this version. The fallback uses a normal call with appended original-caller bytes, not delegatecall; it cannot be set to the Safe itself. The compatibility handler supplies ERC-1271 and token-receiver support. Simulation helpers intentionally revert all delegatecall effects. These observations describe the reviewed empty-module setup and identify the privileged boundaries; they do not approve a future module or guard.

**EXT-DEPLOY-01 — open production verification requirement, not an asserted public exploit.** The wrappers/script require nonempty external code and trustworthy-looking getters, but do not compare Safe singleton, factory, handler or returned proxy runtimes to pinned expected hashes. The existing-Safe shortcut verifies each requested owner is present, not an exact owner set, and does not inspect module/guard/fallback state. A wrong configured dependency can impersonate getters; a previously used authentic Safe can retain privileges absent from these checks. The deployment runbook's independent source/runtime and owner/threshold verification remains necessary before funding or transferring OMERTA ownership. Retain exact full owner set, threshold, nonce, masterCopy, proxy/singleton/factory/handler code hashes, zero-or-reviewed modules, and zero-or-reviewed guard at a pinned chain/block. No production Safe deployment, funding, signature, or mutation was performed here.

## ERC-6551: destination identity and access recovery

The reference registry `account(implementation, salt, chainId, tokenContract, tokenId)` and `createAccount` use the same CREATE2 formula and ERC-1167 proxy bytecode with an immutable footer. Registry account creation is permissionless and repeatable as a no-op once the address has code. Third-party deployment of the identical account does not change its controlling NFT or implementation. A destination can receive ERC-20 tokens before its proxy is deployed; that alone is not evidence that they are recoverable.

The reviewed reference account reads chain ID, token contract and ID from its own code footer. `owner()` returns the current ERC-721 owner on the matching chain. `execute` accepts only that owner, allows only CALL operation, increments state before the call, and bubbles failure; there is no unrelated relayer execution authority. ERC-1271 delegates signature validity to the current owner. Burning the deed makes ownerOf revert and prevents execution; reminting the exact same token ID restores control of the same address and contents to the new NFT owner. An ordinary NFT transfer likewise transfers account control. This matches OMERTA's name-derived StreetDeed token ID and documented retained-vault/reimport behavior.

`resolveTbaOnchain` rejects missing/invalid inputs and a wrong-chain RPC, then queries the configured registry using the configured implementation/salt and StreetDeed token ID. It returns null on read failure. It does not prove the implementation has code, prove bytecode equality, or deploy the account. The registry itself computes addresses even for a nonexistent implementation. Mainnet stock delivery therefore requires exact registry, implementation, salt, chain, and StreetDeed address pins plus one real account binding/recovery check. The vendored account is explicitly test-only and is not selected automatically for production. A successful local stock-delivery proof cannot clear this configuration requirement.

**EXT-DEPLOY-02 — open production verification requirement, already explicit in CHAIN-DEPLOY.md.** Before the first real delivery, verify code/source hashes for the actual registry/implementation, independently derive and query a real deed's target, verify its footer/owner when deployed, and prove the owner can execute a small recovery transaction in the approved rehearsal. A misconfigured implementation can strand counterfactually delivered assets while all unit-denominated conservation checks remain green. This is a trust/configuration boundary, not a permissionless takeover found in the reviewed reference code.

Off-chain target selection relies on the indexed owner and deliberately falls back to the extractor when no owner observation exists. A stale watcher or an NFT sale between destination selection and delivery can transfer control of that target before stock arrives. The account follows the NFT by design; the source review does not prove real-time ownership synchronization. The original code documents drain-before-sale and vault-history disclosures. The coordinating RWA/backend review must retain any ownership freshness and signed-delivery evidence; the reference registry/account cannot solve those off-chain timing questions.
