### INT-DEED-01: exact failure and recovery evidence

StreetDeed `_safeMint` establishes ownership before calling the receiver. The receiver can burn its newly received token, so the actual transaction emits Redeemed before the final Extracted event. Worker streams process these event families independently. If reading/ingesting Extracted fails for one cycle, the worker can still process the confirmed burn. Previously `applyDeedReimport` looked only for a deed already keyed to `onchain:<tokenId>`; failing to find that state caused it to mark the burn applied. A later successful extraction re-keyed the deed, but the consumed burn was never retried.

The correction locks the existing row by token ID, distinguishes an extraction-pending owner from absence of a row, and leaves that burn pending until extraction is indexed. Existing account eligibility, exact burn recipient, one-deed limit and replay rules remain. `test/audit/deed-reimport-order.js` drives the real signing path, schema, watcher cursors, transaction handlers and recovery sweep; only confirmed RPC event input is a fixture. It reproduces the original failure, passes sequentially in pg-mem, and passes two overlapping recovery sweeps against dedicated PostgreSQL 18. Recovery applies exactly once to the recipient and creates no currency-ledger movement. The Solidity callback-order proof is separate actual-contract evidence.

The change prevents new occurrences; it is not a migration that repairs already-consumed historical burns. No production database was changed. If this rail previously ran, a read-only historical reconciliation would be needed before deciding whether any repair is necessary.

### M-01: corrected immutable code and retained proof

The guard executes before any setter writes or event and introduces no external call. Valid nonzero, nonself contracts or EOAs remain supported. A rejecting recipient can still make its sweep revert, while the owner may rotate it and retry; swap liveness remains independent of recipient callbacks. Corrected Hook SHA-256: `aa185334f198da4b12b8661f39ef00b4e17edd10bc2dfbf7dc456d91cd1520b1`. Changed creation code invalidates prior predicted CREATE2 Hook addresses/salts; launch artifacts must be rebuilt from this reviewed source. The correction does not alter an already deployed immutable Hook or recover previously stranded balances.

## External launch and custody integration

The source boundary includes Liquidity Launcher v3.2.0 (`41442a518de9aa2a60ce5db76046dc4c983dd35a`), exact LBP v3.1.1 (`5ef0262b8e191360a212aac864a525dcf7a06605`), CCA v2.1.0 (`a56d42231e7bf048136d9d88fa61e8518c10c5ff`), Safe v1.4.1 (`bf943f80fec5ac647159d26161446ac5d716a294`) and the test-only reference ERC-6551 implementation. The used launcher/LBP source paths were compared across the two launcher checkouts; the relevant implementations agree. External source hashes and paths are retained separately.

The launcher holds pooled balances, so an ERC-20 transfer into it and distribution must be atomic; the OMERTÀ builder uses the required combined call. LBP checks initializer/hook/fee/key/migration configuration, reserves one committed pool ID, and calls its migration body through an only-self subcall. Pool initialization and LP creation are inside that same subcall: a failed LP creation rolls back initialization before the outer recovery branch. This is the needed connection between the Hook's authorized initializer and the splitter's nonzero-pool success discriminator. Migration dust and raised currency are forwarded to committed recipients; native forwarding uses the upstream force-send path. Token and ETH accounting and their recovery recipients are distinct.

Read-only Robinhood mainnet verification at block **57,406,998** matched all six configured runtime hashes—LiquidityLauncher, LBPStrategy, CCA factory, Permit2, PoolManager and PositionManager—and their checked immutable links. The CCA factory controller was zero at that observation. This verifies the configured runtime pins at that block; it is not proof that all upstream source was independently reproduced into matching deployment bytecode. A separate same-block observation at **57,414,349** found ArbSys block number equal to the RPC block number. Local fork clock simulation is a separate assumption and is recorded by its own evidence.

The local stock rehearsal passes 15 assertions using actual deployed reference ERC-6551, StreetDeed and StockVault contracts, signed deed issuance, real ERC-20 delivery and event-based settlement. It uses pg-mem, so PostgreSQL locking is established only by the separately named database runs. It does not select or certify a production account implementation.
